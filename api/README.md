# RestaurantGo API

Laravel API powering the RestaurantGo platform: multi-tenant restaurant management (menus, HR,
payroll, financials), Stripe billing, and the platform's own super-admin operations. See
[`restaurant_saas_plan.md`](../restaurant_saas_plan.md) at the repo root for the original schema/architecture
plan, and [`../DEV_CREDENTIALS.md`](../DEV_CREDENTIALS.md) for local demo logins.

Two frontends consume this API — see their own READMEs:
- [`../dashboard`](../dashboard) — the tenant admin panel and each restaurant's public menu/blog (port 5173).
- [`../web`](../web) — the company marketing site, directory and super-admin panel (port 5174).

## Stack

PHP 8.4, Laravel 13, Sanctum (token auth), Spatie Permission (roles/RBAC), Stripe (billing),
Pest (tests), Scribe (API docs), MySQL (SQLite for tests).

## Local setup

```sh
composer install
cp .env.example .env
php artisan key:generate
```

Point `DB_*` in `.env` at a MySQL database (or leave `DB_CONNECTION=sqlite` for a zero-config local
DB), then:

```sh
php artisan migrate --seed
php artisan serve          # http://localhost:8000
```

The seeders create a super-admin account, a demo tenant, and several more demo restaurants —
credentials are in [`../DEV_CREDENTIALS.md`](../DEV_CREDENTIALS.md).

### Queue worker

Transactional email (`app/Notifications/`) is queued (`QUEUE_CONNECTION=database` by default), so
nothing actually sends until a worker runs:

```sh
php artisan queue:work
```

### Docker

`docker compose up --build` from the repo root brings up `api` + `queue-worker` + `mysql` +
`dashboard` + `web` together — see [`../docker-compose.yml`](../docker-compose.yml). Requires an
`api/.env` to already exist (copy `.env.example` first); it's bind-mounted into the container as-is,
so the same file drives both native and Dockerized runs.

## Testing

```sh
vendor/bin/pest
```

Tests run against SQLite in-memory (`phpunit.xml`) with `QUEUE_CONNECTION=sync` and
`MAIL_MAILER=array`, so queued notifications execute synchronously and are assertable via
`Notification::fake()`.

## Architecture notes

- **Multi-tenancy**: `IdentifyTenant` middleware resolves the current tenant (authenticated
  user's own tenant → custom domain → subdomain) and binds it into the container as
  `app('tenant')`. Tenant-scoped models use the `App\Models\Concerns\BelongsToTenant` trait, which
  adds a global scope + auto-fills `tenant_id` on create whenever a tenant is bound — this also
  covers implicit route-model binding (`{model}` route params), not just explicit queries.
- **Platform vs. tenant**: `/api/admin/*` is a separate area for internal company staff
  (`tenant_id === null` users), gated by `EnsurePlatformStaff` + Spatie `permission:` middleware —
  entirely independent of any tenant's own HR/employee tables.
- **Billing**: Stripe Checkout + Billing Portal (`app/Services/StripeService.php`), with the
  `subscriptions` table kept in sync via signature-verified webhooks
  (`app/Http/Controllers/Subscription/WebhookController.php`). Paddle is schema-only, not wired.
- **Auditing**: most write actions go through `AuditService::log()`, recorded in `audit_logs`.
